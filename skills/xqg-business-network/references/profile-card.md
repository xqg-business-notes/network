# 档案卡规范

用户主动要求登记，或接受“让其他创业者找到你”的资源建档邀请并提供资料后，再按已有业务、需求和供给出草稿。用户只在查询或补充匹配细节时，不抢先做卡片，不要求先填表才能推荐。可接受公司介绍、产品资料等自由表达；只补问影响理解的关键内容，不逐项盘问。拒绝或不回应建档邀请时继续原服务。

在聊天中输出完整的资源档案，使用纯文本代码块，短段落配【栏目名】，方便复制到微信；不使用表格、星号、层层缩进。用户需要文件时另提供同内容的 Markdown 文件，但不能只给下载链接而不给可复制正文。复制按钮是否存在取决于客户端，不声称所有客户端一键复制。

按本人真实表达填写，不为填满字段补充想象。没有填写、尚不明确、明确没有、不愿公开、不限条件不同，不能互相替换。本人尚未确认的新内容先标“待确认”；日期使用当前环境可靠日期和用户时区，没有日期能力就询问，不编造。只有本人完成确认后才填最新确认日期。初稿优先只显示已知业务、可提供的资源和当前需求，称呼未知可写待补充；编号、展示意愿、日期等在确认版再补，不用一屏空栏目。以下是确认版可用的字段模板，不是首轮必须问完的清单或已登记样例：

```text
【创业者合作档案卡】

人员编号：待登记分配
称呼：
城市：

【当前业务】

【能提供的资源或服务】

【希望获得的帮助】

【合作条件】

【展示与引荐意愿】
待本人确认。

【最近确认日期】
待本人确认。
```

字段可按内容自然调整。例如线上/线下、首次体验方式、最低订量，在相关服务或需求下分段写；没有必要保持固定总字数。对多项资源/需求分别用短段落，一人允许多项。需求与资源可以同时登记，也可以只留下其中一类；将需求写成希望解决的具体事情，将资源写成能够实际提供的产品、服务或帮助。没有明确需求时如实写“暂未明确”，不制造虚假需求。

最终确认前，按 registration.md 用本地预览脚本展示脱敏公开版；本人完整卡片保持原名用于核对，公开预览保留星号。最终询问一次：“这份资源档案和公开展示内容准确吗？有没有不愿展示的内容？确认后，我会将这份档案保存到网络数据库；待小强哥在微信上确认后，再开放给其他创业者查询匹配。”在得到用户明确确认前，不执行正式登记。若已有明确回答，不重复索要相同确认。

用户后续又补充需求，需展示合并后的最终卡片并确认。本人确认后，读取 [确认入库流程](registration.md)，调用正式登记接口，收到 saved=true、registered=true 和真实 person_id 后才说“你的资源档案已通过 AI 系统保存到数据库，编号是……”。将编号写回完整确认版，在聊天里用纯文本代码块再次展示，便于复制；不能只输出编号、增量字段或文件链接。

保存后说明“微信确认后开放匹配”，并提醒：“请务必添加小强哥微信，把上面的资源档案复制发给他，方便其他创业者有相关需求时，小强哥能及时联系你、协助对接。”随后单独展示微信代码块 xqiangga。已加过微信，直接发送档案即可。不要再加“认识一下”或“以后有需要资源时直接找他”。不要把微信引导、技术状态或系统内部备注混入个人档案。

编号只能使用正式登记接口或管理员真实返回的 A 编号。确认内容、保存聊天记录、提交摘要或生成 Markdown 文件本身都不等于正式入库。登记失败不能编编号或声称成功；服务未支持登记时如实说明尚未入库，仍可提供已确认卡片和微信人工登记路径。内部存档与开放匹配分别以真实回执为准。

未登记编号、未发生的后台保存、未核验履历都不补写“已确认”。原有成员的最新个人卡片只能来自本人提供、当前可靠上下文或授权身份读取；公共搜索到的同名人不是其私密旧档案。

演练卡片标明“演练，未登记”，不作为真实资料归档。用户没有明确结束演练时，“可以”“不用改了”“每天一次”仍属于演练对话。

## 资料型档案

有产品手册或案例时按materials-and-cases.md组织“概况—产品服务—案例—需求”，不把所有内容压进短卡。首次可先展示概况与条目索引，再给完整公开预览；最终确认覆盖实际拟提交全文和链接。原始材料和未授权的客户信息不进入公开字段。
